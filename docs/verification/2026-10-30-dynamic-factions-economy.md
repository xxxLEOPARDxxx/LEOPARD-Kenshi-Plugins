# Dynamic Factions: проверка физической экономики 30.10.2026

Статус: локальная проверочная сборка. Полный игровой рейс и повторная загрузка
с товаром пока не приняты. Публикации Nexus/Steam для DynamicFactions не было.

## Реализация

- Runtime использует экономические правила без почасовой выплаты и без покупки
  абстрактных очков технологий. Стартовый бюджет остаётся явно заданным сценарием.
- Штатный OPERATE_MACHINERY производит настоящую руду. HAUL идёт к жиле,
  переносит фактические единицы в обычный инвентарь/рюкзак, идёт к торговцу,
  передаёт ему товар и получает деньги из его кошелька в казну своей фракции.
- Цена вычисляется в контексте настоящего торговца/города. Глобальное окно
  торговли игрока не используется. Исследованы контракты native функций из
  KenshiLib, включая опасный глобальный контекст getValueSingle(false).
- Передача проверяется по количествам сторон, оплата по обоим кошелькам.
  Подтверждённый отказ компенсируется. Неоднозначная частичная мутация блокирует
  работу без слепого повтора; workFault переживает сохранение/загрузку.
- Старые виртуальные остатки сохраняются совместимо, но не производятся, не
  складываются с настоящим запасом и не продаются. Учёт груза и денег остаётся
  в штатном сейве игры; runtime-задачи после загрузки восстанавливаются из него.
- Метаданные и handles инвалидируются до смены мира. Ready зависит от завершения
  штатной загрузки. Работа не исполняется на паузе или внутри сохранения.
- Один пространственный запрос на шаг фракции вместо запроса на каждого рабочего
  и жилу; рабочий шаг не чаще раза в пять секунд без паузы. Native переносы
  ограничены 64 единицами за вызов. Это границы работы, а не замер времени CPU.

## Воспроизводимые проверки

Из корня ours:

```powershell
& ./DynamicFactions/tests/build_tests.ps1
python ./DynamicFactions/tests/run_session_tests.py
& ./build.ps1 -SrcDir D:/DEV/Kenshi/ours/DynamicFactions -Name DynamicFactions -SubDirs @('core','game','ui')
```

- Ядро: 1051 проверка, 0 ошибок. Проверены повреждённые состояния, NaN/overflow,
  duplicate ID, ограниченные/полные инвентари, частичная продажа, бедный торговец,
  границы целых, переходы ролей, сбои до/после мутации, возврат товара/денег,
  отсутствие пассивного дохода и модель повторной загрузки на фазах перевозки.
- Извлечённые реальные функции: 18 проверок, 0 ошибок. SEH до/после списания и
  смены фракции, отказ возврата, повторно использованные handles, поколение
  сессии, отмена старой задачи и прибытие разведчика на склоне.
- Сборка VC10 x64 проходит. 108 импортов проверены по установленным экспорту
  KenshiLib/MyGUI/Ogre. KenshiLib.dll побайтно совпадает с официальной 0.5.0;
  см. ../dependencies/kenshilib-sdk-audit-2026-10-30.md.
- EN/RU/CN: по 62 записи в MO, включая заголовок; gettext readback проходит,
  все используемые Tr-строки покрыты. Личный INI сохранён; Debug по умолчанию 0
  в распространяемом шаблоне, в пользовательской проверочной сцене включён.

Чистые тесты используют модель инвентарей. Они не доказывают фактическую
проходимость пути NPC или исполнение native торговли в игровом мире.

## Наблюдения в настоящей игре

Первая проверочная DLL 329216 байт, SHA-256
`8203b2330c5247d331ad643ed5a741111f0cc530a246d9e6e30ff073f51a13f4`
была установлена с резервной копией прежних файлов. В новой сцене у Хаба
основаны «Железные Клинки», наняты два местных рекрута: 20000 -> 17000 -> 14000.
Последующие часовые тики сохраняют 14000. Слот DF-cycle-test содержит файл
фракции с founded=1, workFault=0 и двумя подтверждёнными событиями найма.
Полная загрузка этого слота с грузом ещё не проверена.

Read-only исследование ближайших 56 ячеек и 6 загруженных зон обнаружило семь
настоящих природных жил в радиусе 3000 м. Их raw owner — точный служебный nofac,
а не NULL. Прежний фильтр ошибочно отвергал все семь. Исправленная общая
проверка открытия/забора использует FactionManager::getEmptyFaction; native
реализация делает только поиск nofac, не создаёт фракцию. Иные нейтральные
владельцы не получают разрешение автоматически. Ближайшее железо в 1694.53 м
от Хаба; зафиксированные разведчики ещё не были в 300 м от него.

Дополнительно исправлено прибытие разведчика: целевая высота бралась от Хаба,
но склон выше на 52 м. Полная 3D-проверка не признавала достигнутую точку и
ждала 60 секунд. Проверка XZ воспроизведена извлечённой функцией: до исправления
17 проверок / 1 ошибка, после 17 / 0.

Вторая кандидатная DLL 329216 байт, SHA-256
`ec8aea72bc6294d348e7ac0f7743735be67589767926ec8740c1710e2195f204`.
До установки дополнительно воспроизведён абсолютный 60-секундный тайм-аут
дальнего перехода: он менял цель даже у движущегося разведчика. Теперь точка
меняется после прибытия или по общему контролю отсутствия прогресса 30 секунд,
который пропускает действительно недостижимый маршрут. Регрессия 18 / 1 -> 18 / 0.

Актуальная DLL 329728 байт, SHA-256
`0615f16eed508e157415ea05d6c27d0b245ec97ff15bfc7dae33c5e8ed6b3ff1`.
После подтверждения пользователем выхода из игры DLL установлена. Перед
заменой повторно проверены отсутствие процесса Kenshi, SHA-256 кандидата и
108 native импортов. Установленный файл побайтно совпадает с кандидатом.
Личный INI и dynamicfactions.txt в DF-cycle-test сохранили прежние SHA-256;
первая DLL отдельно сохранена в economy-install/candidate-1.dll.
Запись установки: economy-install/INSTALL-CANDIDATE-3.json.
Ожидается загрузка DF-cycle-test для продолжения игровой приёмки.
