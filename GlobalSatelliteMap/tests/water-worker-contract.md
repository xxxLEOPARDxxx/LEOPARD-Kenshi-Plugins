# Water-source worker and window-height metadata, 2026-11-02

Scoped implementation changes only `GsmAtlasJob.h` and `GsmAtlasManifest.h`. No game/Ogre/UI call, renderer, setting, JSON field, cache format or installation is added. The main-thread caller, generator and water renderer are owned by root.

`Job::waterValidation` defaults false. A dedicated water job sets it true, leaves `validation=false`, supplies the current absolute game directory with trailing separator, and receives its usual generation stamp from the existing launcher. `Run` refuses both mode flags together. The water branch hashes every generated `GsmWaterShaderInputs` path/SHA using the existing guarded `HashFile`,64KiB cancellation/progress checks and a **16MiB cumulative file-size/read allowance**. The generator currently supplies the five exact NativeWater source pins. It does not enumerate game/mod trees, hash the atlas, call native code, load textures or log from the worker. Missing/corrupt/oversize sources and cancellation fail with the fixed existing error buffer. `Manifest::waterVerified` defaults false, is set only after all hashes and final generation/cancel checks pass, and is retired on every failed/cancelled water job. It is a memory-only acceptance flag; Ready JSON does not supply it.

Main-thread integration must handle `job.waterValidation` separately before terrain/window adoption: accept the flag only for the still-current successful generation and merge it into the existing terrain manifest. Do not replace that manifest with the water job's otherwise empty manifest; do not call terrain `Fail` on a water-source mismatch. Terrain remains usable while water is unavailable. Keep the existing single outstanding worker ownership/cancel/join contract. Schedule water validation once per required generation/profile change and latch failures; the false flag alone must not cause continuous file retries. This change does not supply that scheduling or UI logic.

Only successful `ReadWindow` jobs call `WindowMinimum`. The function verifies exact256x256 RGBA8-coverage/R32-height plane sizes, reads each height with `memcpy` (no alignment/alias assumptions), and considers only A>0 plus finite height. Zero coverage, NaN and either infinity do not contribute. It allocates no array, performs no I/O and publishes only `windowHasFiniteHeight`/`windowMinHeight` after the complete scan. An empty valid set publishes false/0; shape/cancel failure leaves false/0. There are exactly65,536 sample iterations and generation/cancel checks every4,096 samples plus completion. Main-thread entries may retain those two scalars before clearing the CPU planes, then compare them against the actual current absolute native waterY to decide whether a window can contain water. This is a conservative coarse-window eligibility summary, not per-pixel coastline rendering.

`Run` resets old success/error/minimum state on entry and invokes the summary only after a successful window read. Water and full terrain validation jobs never scan window pixels. No per-frame scan or allocation is introduced; all new pixel work happens on the existing file worker. Static bounds do not measure FPS or whole-process memory behavior.
